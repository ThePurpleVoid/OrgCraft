# Changelog

## Unreleased

- **Server: quiet hours, a daily digest and the delivery log** (PRD O3, O6, L25 server half). `GET/PUT /v1/me/notifications` holds each person's time zone, quiet hours (local times, may wrap past midnight) and daily digest (a local time and the kinds to gather). During quiet hours an email that does not break through (approvals and budget stops do) is logged `held` instead of sent. A new email kind, `digest`, sends one email a day at the person's own time with what was held plus the kinds they picked (at most 20 lines, then "And N more"); its unsubscribe link turns off the digest. `GET /v1/teams/{team}/notifications/log` lists email and Slack tries, newest first, with masked addresses; you see your own, `all=1` needs admin. Migration 019 (`notification_prefs`, a `held` flag on email deliveries). Contracts additive. **What existing teams see:** nothing until someone sets quiet hours or turns the digest on.
- **Runner: the sidecar for local MCP servers** (F4, L20 runner part). A connector with a `command` now runs in the runner's sidecar instead of inside the agent's process. It runs as its own process, as a user of its own from the runner's pool (never the runner's, never the session's), with only PATH, a private HOME and its own secrets, which the runner asks for by name with `secret.get`. The agent reaches it through a loopback endpoint with a token for that session, and never sees a secret. Only calls the policy allowed run, and each runs once. Each call carries an idempotency key made from its call id. Results are capped at 64 KiB and redacted. The manifest's `effects` set each tool's effect: send, destructive, payment and deploy wait for a person, and so does a tool with no effect. A runner without separate users refuses command servers. A community server runs only where its egress list is enforced. Contracts additive. **What existing teams see:** nothing, until the control plane sends a local server in `tools.mcp`.
- **Runner: sign-offs name the version they checked, say what they did not check, and carry the runner's own evidence** (governance G1 and G2, review 2 AI-1, L23 runner part). The `signoff` tool gains `version` (a full commit id, or a document or draft revision) and `versionKind`; a short commit id is refused. `report`, `handoff`, `bug`, `signoff` and `blocked` gain `unverified`: an empty list means `Unverified: none`, leaving it out means not stated. Every sign-off carries `checks`, the calls the session ran and saw succeed, recorded by the runner (never the model), with the call ids the run inspector shows. Contracts additive. **What existing teams see:** nothing changes until a role names a version or an unverified list; the gate that refuses stale or partial sign-offs is the server's part.
- **Runner: step boundaries and step I/O for the run inspector** (N1, ADR 0009, L19 runner part). Every tool call gets a `call` id, an `effect` and, when it repeats a failed call, `retryOf`, all set by the runner; an allowed call ends with a new `session.result` (ok, duration, a short redacted summary). When the team captures steps (`session.start.caps.capture`: all or tools), the input, the output and (with all) each turn's own text go out as `step.io` frames, redacted with the secrets' names and cut at 64 KiB, and the turn's events name their wake as `cause`. The Agent SDK adapter gains a PostToolUse hook that only observes. Contracts additive. **What existing teams see:** nothing until the control plane turns capture on.
- **Runner: two teammates of one role are two sessions** (ADR 0011, L17 runner part). `session.start` may carry `type` and `name`; the prompt says "You are Maya (support-agent-2), a support-agent", and teammates still address it by its member id. Memory, working copy, branch and agent user all key on the member id, never the type, proven by a runner test with two members of one type (two uids, two copies, two branches, two memory files, neither readable by the other).
- **Renamed to OrgCraft** ([docs/renamed-to-orgcraft.md](docs/renamed-to-orgcraft.md)). The package is `orgcraft`, the command `orgcraft` (with `agent-team` kept as an alias), and the README, CLI messages, the Studio's pages and email, the publish trailer (`via OrgCraft Studio`) and the generated-file marker all use the new name. `.agent-team/`, `docs/team/`, `scripts/agent-team/`, the `AGENT_TEAM_*` settings, the `agent-team:start` markers and the `agent-team/…@1` schema ids keep their names on purpose. Readers accept files generated under the old name. **What existing teams see on sync:** the kit's name in generated headers, the generated README and the protocols. Nothing else.
- **Control plane: resuming a paused run needs step-up, whoever paused it** (ADR 0013, local PR L7). Before, only a run the budget paused asked for a passkey, so anyone holding a session could restart a run the owner had stopped to think. The step-up is bound to that run: `POST /v1/auth/step-up` takes an optional `scope` (here `resume:<run id>`, named in the `step-up-required` answer), and a resume refuses a step-up made for anything else, which stays unspent (migration `014_step_up_scope.sql`). A host may still pause or stop a run but never resume one. Stopping and pausing stay one tap with no step-up, and a person's pause is never lifted by the day rolling over. The audit row for a resume says who paused the run (`pausedBy`). The Studio (local and hosted) passes the scope through when it asks for the passkey or secret.
- **An approval is bound to the exact call it covers** (ADR 0013 rule 1, runner side; local PR L6). Before, `request_approval` ended by telling the model to "go ahead with exactly that call": an instruction, not a binding. Now:
- **Control plane: an approval is bound to the exact calls it covers** (ADR 0013 rule 1, server side; local PR L6). The server re-canonicalises the calls a session names, checks their hash, and renders the card's facts from them (never from the role's text: two duplicate keys can make text read "jane" while "attacker" is signed). A fact is shown whole; a call too long to show is refused with "split it" (422), since a cut could hide its recipient. Risk is the server's (bound calls are high), the step-up that approves is scoped to the tenant, team, approval, card version and calls (`approve:<hash>`), and `approval.result` echoes `callsHash`, also on a resend, so the runner now requires it by default (`ORGCRAFT_SIGNED_CALLS=0` for an older control plane). Migration `015_approval_calls.sql` (additive). The canonical form lives in `packages/calls`, shared by both. **What existing teams see:** cards for held calls say "It will do exactly this" above the teammate's reason.

Event ids are unique only within a team, and some are deterministic (`published-<sha>`, and the planned schedule slots), but deliveries were unique on `(event, role, instance)` with no team. A second team with the same event id, in the same tenant or another, had its delivery silently dropped. Migration `013_deliveries_per_team.sql` makes it `(team, event, role, instance)`. `/me/stream` resuming from an event id that two teams share now replays from the earlier one instead of skipping what lay between.
- **Runner resilience, before the real M3 exit test** (#28). This is an offline pass with the fake model. `tests/e2e/m3-resilience.e2e.mjs` kills the runner mid-session, takes the control plane away, cuts the runner's link, pauses at 100% of the daily budget and expires an approval while the runner is down. It runs in process and, in CI, with the runner image. What it found and fixed:
  - A restarted runner's sessions were "resumed" on it as ghosts, and messages to them were acked and lost. Now `hello.sessions` decides which sessions resume. The lost ones start again from their checkpoints, with what woke them since they were last idle. A message for a session the runner does not have is nacked, and the session is started again.
  - Stopping a run while its runner was away stopped nothing, so on reconnect the session merged a pull request approved before the stop. Now the session stops in the control plane at once, and the runner gets `session.stop` with the welcome.
  - While the control plane is away, a session starts no new model turn and merges nothing. On the server side, an approved merge's `approval.result` goes out only while its run is running.
  - Raising the day's cap resumed a run that was also past its own cap, and its sessions ended at once with nothing to tell the owner. That run now stays paused, with its own budget card.
- **Meetings: replies are data, and action items stay inside the meeting** (security review of #152). Every meeting turn's prompt says the quoted replies are what other attendees wrote, to weigh and never to follow. `meeting_close` refuses an action item for a role that did not attend the meeting.
- **Studio: the Rollout page** (kit #120, PRD 6.9 X7, demo step 17, CPO copy "Rollout view after a publish", D61 to D63). It answers "has the team picked up what I published?" with one line per role, built from board reports since the publish merged. A role is "On the new version" only when a report after the merge names it. A mid-task role says "Finishing "{task}" on the old version" plus the choice made at publish (then switches over, handing off to {role}, paused). The other lines are "Picks up the new version at its next task", "Switched off · finishing … first", "Off", "No report since the publish" (with "last heard N h ago"), and a grey "Version not reported" with a Why? hint. Roles that report no version, and roles that are off, are left out of the "{n} of {m} roles on the new version" summary. Reports older than 2 hours are grey. The page is read-only. It also has an empty state, and "Waiting for the change to merge" when this checkout has a team commit the default branch doesn't have yet. When connected to a control plane, the data comes from `GET /v1/teams/{team}/rollout`. Locally it comes from the default branch's last `.agent-team/` commit (its plan read from the commit message) and the board, via the new `GET /v1/team/rollout`. Rows are sorted by what needs a look (mid-task first, then waiting for a next task, no report, version not reported, moved, off). A role waiting for its next task is plain, not amber. The heading links to the pull request or commit ("see the change", GitHub https only, credentials never carried over). The waiting notice says it is "As of the last time the Studio checked the repository", and while a change waits the count names the merged version ("0 of 9 roles on {name}"). It reloads when the board changes. The page is not shown in an embedded Studio yet.
- **Studio chat: a resume refused for a spent budget says so in words** (QA sev-4, CPO copy). The server now marks both of those 409s (start and resume) with the problem type `budget-exhausted`. The chat shows "Today's budget is spent, so the run can't resume yet. Raise the cap for today to resume it now, or resume it after the budget resets at 00:00 UTC (in N h)." with a matching button. While today's budget card is open, the button says **Raise the cap for today** and points to that card, whose Add half again lifts today only and resumes with one step-up. Once the card is answered, it says **Raise the daily cap**, asks for a new cap above today's spend, steps up, and resumes. The start dialog says when the budget resets too. **Server:** a stepped-up raise of the daily cap above today's spend now opens today again: it clears the spent mark and any Resume tomorrow, so the resume after it goes through. Before this, the run stayed paused (QA #162 sev 2). The spent sentence goes away once the run is going again, and a cap that is too low, or not an amount, keeps the sentence and its button. The step-up dialog's Confirm waits while a check runs, so a double tap no longer gets a 429.
- **The kit names no product in anything it ships** (`tests/handoffs-out.test.mjs`). `handoffs/`, the kit team's mailbox with products that use the kit, never ships in the package, init or sync output, and no product name the kit team has a mailbox with appears in a shipped file. A comment in the board's CSS lost the product it was ported from.

The dry run has a discussion, proved end to end with the fake model.

## 0.20.0

- **Control plane: delegated publish, the Studio inside your own app publishes through the deployment** (`docs/specs/studio-embed.md` section 6, issue #123). A host's token may now use the hosted Studio routes (read, preview, suggestions, graph, templates, publish), on installations the workspace proved it owns (S9) and with the person's own role. A change to commands the team runs is never published through a host, even by an admin, because a host's token carries no step-up. Publishing needs the person's yes on the new consent text, which says the host "can open pull requests that change your team" (migration `011_host_consent.sql`; an older link keeps reading and is asked again on the next sign-in). The person is the actor and the commit trailer; the host's own user (`x-agent-team-host-user`, cleaned) appears only in the PR body and the audit detail. Each host may publish 10 times in 10 minutes and preview 60 times a minute. In the kit's handler, `authorize` may return `via: { host, user }`, which the PR body names (`core.cleanVia`).
- **Control plane: an event dated in the future is stored at the time it arrived** (security review of #149). An event whose `time` is more than five minutes after the server's clock is stored with the time the server received it, so a future-dated `usage.recorded` (from an integration or a runner) can no longer spend, warn about or exhaust a day that has not come yet. Up to five minutes of clock skew is kept as sent.
- **Control plane: `POST /v1/teams/{team}/events` takes an allowlist** (issue #135, security follow-up on #131). Only what an integration reports is taken: `report.*`, `message.*`, `usage.recorded` and the Studio's fast-path `team.published`. Every type the control plane or a runner writes itself (chat, approvals, decisions, cards, Ready to try, runs, sessions, proposals, budgets, meetings, connectors, notifications) is refused with 403, and one such type refuses the whole batch (`refused` lists them). So no admin token can make the chat or the clients show something the system never said. Also from the security review of #148: `GET /v1/github/installations` marks `proverLeft` when the person who proved an installation is no longer an owner or admin here.
- **Control plane: GitHub App installations each workspace has proven it owns** (`docs/specs/studio-embed.md` S9, issues #123 and #139). The deployment's GitHub App key can mint tokens for every customer, so a token is only ever used for an installation bound to the tenant. An admin connects one with `POST /v1/github/installations` (step-up): the app's install page with a signed, single-use, ten-minute state. GitHub sends them back with a user code, and the binding is made only if GitHub says, as that person, that they are the GitHub user they sign in with, the installation is in their list and not suspended, they administer its account, and they can push to every repository it holds; the user token is revoked straight after. One workspace per installation. `GET` lists them, `DELETE /v1/github/installations/{id}` (step-up) disconnects, and the webhook (`/v1/github/webhook`, `GITHUB_WEBHOOK_SECRET`) disconnects an uninstalled or suspended one at once. `PUT /v1/teams/{team} { repo }` names the team's GitHub repository, which the hosted Studio uses (its `teamRepo` and `boundInstallations` now come from here, and `bin.mjs` turns it on with `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY`). A run on a github.com repository whose account is not proven gets 409 `type: installation`; `session.start` carries the proven ids as `repo.installations` for the runner (#139). New env `GITHUB_APP_SLUG` and `GITHUB_WEBHOOK_SECRET`; migration `010_github_installations.sql`. Off without `GITHUB_APP_SLUG`, so local mode is unchanged.
- **Control plane: hosts and stream tickets, for the Studio inside your own app** (issue #123 step 2, docs/specs/studio-embed.md section 6, S4 and S8). An admin registers a host with `POST /v1/hosts` (step-up). It is a confidential OIDC client of the deployment's issuer: client secret shown once and kept sealed, PKCE, DPoP-bound tokens. A host's token can use the Studio's own routes, never step-up, passkeys or the host registry, and revoking the host ends its tokens at once. `POST /v1/teams/{team}/stream-tickets` gives a single-use, 60-second ticket that the host's page uses to open the team's live stream directly, with CORS for that host's origins only and no credentials; the stream ends when the person is removed or the host revoked. Migration `009_hosts.sql`. Sign-in must be on; local mode is unchanged.

  - **Connecting your account:** "Connect Slack" signs the person in with Slack (identity only). The new `/slack/callback` page (`slack-callback.html`, rewritten by `build.mjs --studio`) links the account and returns to Notifications. A cancelled, forged or expired sign-in says what to do.
  - **DMs:** the same switches as email, with the suggested two ticked but not saved until Save (D49). After that each switch saves at once.
  - **Health line:** "Slack · working", or "failing since …, sending by email instead".
  - **Disconnecting:** "Disconnect Slack" asks to confirm first.

When the same copy resumes on another user, the runner hands it over itself; nothing runs as an agent user that is serving someone else. The user is checked empty before it is used again; a user that does not come back empty stays out of the pool. At startup the runner checks every agent user, checks that one cannot read or list another's folder, and requires `fs.protected_hardlinks=1`. The older single `AGENT_TEAM_SANDBOX_UID` still works but serves one team only. Conditions A to F from the security review. The end-of-session clean-up runs in a child process, so a large working copy never stalls the other sessions, and the image runs `tini` as process 1 so no zombie of an agent user is left behind.

### Runner

- **The runner reads which model each tier runs on from `packages/model-prices`**, the kit's one price table, through `tierModel` (runner config overrides still apply). When the SDK reports no cost for a turn, it uses the table's list price instead of zero, and a model the table does not list is priced as its dearest model, so the budget never counts a turn as free. The runner image now includes `packages/model-prices`.
- **The dry run's chief of staff asks the owner one decision** (exit test step 7): where the change should go, with two options and a recommendation. When the answer comes back, it says what was chosen. The CI test answers that card through the Studio (qa-web's Pass A report). Pass A in CI also runs with the runner image, which exercises the sandbox, the branch-only push and the merge outside the sandbox without a key.
- **A head the runner did not push is checked before any card names it** (#93). When a pull request's head moves after an approval, the runner fetches the new head itself and runs the checkpoint checks over every commit from it back to the bases it fetched: ownership, symlinks, large files and the secret scan. Only then does it ask again. If the checks fail, there is no card: the run gets `proposal.failed` with reason `checks` and the rule in `detail`, and the session is told not to merge another way.
- **Merge approvals name the pull request and the full head commit** (#56, D1). A merge is pinned only as exactly one `gh pr merge <N> [--squash|--merge|--rebase|--delete-branch] --match-head-commit <40 or 64 hex>`, or the GitHub merge tool with `owner`, `repo`, `pullNumber` and `expectedHeadSha`. Anything else that would land on the main line is refused, including a direct push. The tool's `owner/repo` must be the session's own repository, and `approval.wait` carries `pr`, `headSha` and `repo`.
- **Resume from a checkpoint.** A `run.resumed` wake tells the role the run was resumed, and why. `session.started` for a resume says whether the checkpoint commit is on the branch (`checkpoint: { commit, found }`), and a missing one is named in the role's first prompt.
- **Plain http only to a local host.** `register` and `start` accept https anywhere, and http only to `localhost`, `127.0.0.1`, `::1` and `host.docker.internal`.
- **The runner opens and merges pull requests itself** (runner-protocol, Proposals; D1, D2). After a session's first checkpoint push it opens the branch's pull request with the merger GitHub App (`AGENT_TEAM_MERGER_APP_ID` and its key) and emits `proposal.opened`, then `proposal.updated` as the head moves. A `request_approval` with action `accept` checkpoints first and names the pull request and pushed head. On approval, the runner merges pinned to that head and emits `proposal.accepted` with the merge commit, or `proposal.failed` with head-moved, checks or conflict. If the head moved after the approval (someone pushed to the pull request), nothing is merged: the server supersedes that approval, and the runner asks again naming the head that is there now, so exactly one open card names the head that would be merged (code review of #66). Contracts: **a recorded exception to rule 7**: runner-protocol.md's Proposals rule changes who re-asks on `head-moved`; the server now only supersedes, and the runner asks again naming the current head. Changed before 1.0, before any runner outside this repository implements it. A shell merge from the session is refused. `AGENT_TEAM_PROPOSALS=local` keeps the pull requests on a stand-in bare repository for the dry run.
- **M3 on a Mac** (apps/runner/README.md): the control plane, Studio and runner on one Mac. The deploy key and merger app key are installed into the runner's closed folder from a one-off container, and the git config pushes over ssh with a pinned GitHub host key.

- **The M3 dry run** (exit test Pass A; `tools/dry-run/m3.mjs`): one command brings up the control plane (PGlite in the folder), the Studio and a runner with a scripted fake model, against a fresh minimal team whose remote is a bare repository on disk. No model, no key, no GitHub, no cost. `up` prints the Studio link and the step-up secret; `signoff`, `hold`, `move-head`, `release`, `spend <usd>` and `status` steer it from another terminal (QA's SIGNOFF, a push after approval for step 9b, a turn past the cap for step 11, the pull requests with their heads and merge results). `--runner docker` uses the runner image. The runner takes `AGENT_TEAM_RUNNER_ADAPTER=dryrun` with `AGENT_TEAM_DRYRUN_CONTROL`, and refuses it while `ANTHROPIC_API_KEY` is set.
- **CI walks it end to end** (`tests/e2e/m3-dry-run.e2e.mjs`, in process and with the runner image): a chat request, the daily cap and approval with step-up through the Studio's API, a pull request, an approval card naming it and its head, and a merge pinned to that head; step 9b, where a push after approval stops the merge and only the new card's head merges; and step 11, where a turn past the cap pauses the run with a budget card.
- **After a merge, a session starts again from the new base.** The runner deletes the merged branch (as GitHub's delete-branch-on-merge; the merger app's token can) and resets the session's copy to the base, so its next change opens a new pull request instead of conflicting with its own squash. It stays on the branch when the delete fails (a ruleset, say) or when files are left uncommitted outside its areas. A branch that changes nothing against its base gets no pull request (a role that only talked).

## 0.9.2

### Security

- **DNS rebinding on the local dashboard and the Studio (severity 2). Every team should sync to 0.9.2.** A web page on a hostile domain whose DNS name resolves to 127.0.0.1 could call `scripts/agent-team/dashboard.mjs` or `agent-team studio` as if it were the same origin. It could read the board, post reports, and use the token these servers hold for a hosted board (`TEAM_READ_TOKEN`) or the control plane. Both servers now check the `Host` header on every request, static files included, before anything else runs:
  - Bound to a loopback address, they answer only `localhost`, `127.0.0.1` and `[::1]` (any port).
  - Bound to another address, they also answer that address. On `0.0.0.0` or `::` that means every address of the machine.
  - Each server also answers the names in its own allowlist, `DASHBOARD_ALLOWED_HOSTS` or `STUDIO_ALLOWED_HOSTS`.
  - Anything else gets 403. The Studio's Origin and JSON checks on POSTs stay as they were.
- **What existing teams see on sync:**
  - A new file, `scripts/agent-team/hosts.mjs`.
  - Threads on other machines that report to a dashboard started with `--host 0.0.0.0` keep working when they use its IP address. If they use a name (`TEAM_REPORT_URL=http://mac-mini.local:4747/...`, a VPN or tunnel name, a reverse proxy), set that name in `DASHBOARD_ALLOWED_HOSTS` on the dashboard machine; until then those reports get 403.
  - The hosted board, the exported dashboard and CoachSpotter-style sites are not affected. Neither are reports written to the local log.

## 0.4.0

Closes the gaps against other agent kits: reports no longer depend on the roles remembering, the team runs as a Claude Code agent team, the day-to-day path needs only Node, and there is a smoke test.

- **Hooks report for the roles.** `"hooks": true` in `team.json` (the default for `init`) makes sync merge the kit's hooks into `.claude/settings.json`, keeping everything else in that file; `check` fails when they are missing. `scripts/agent-team/report.mjs hook` turns Claude Code events into board reports with `"source": "hook"`: `working` on session start and on a prompt (a waiting, blocked or in-review role keeps its status), a heartbeat at most every 5 minutes while tools run, `idle` when a turn or session ends, and every subagent or teammate as its own role (`SubagentStart`/`SubagentStop`, `TeammateIdle`, `TaskCompleted`). The main session is the role in `AGENT_TEAM_ROLE`. Built-in agents such as Explore are not reported. The dashboard's feed marks hook reports "auto".
- **Claude Code agent teams.** `"agentTeams": true` installs the roles as teammate types in `.claude/agents/`, sets `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in `.claude/settings.json`, and writes `docs/team/agent-teams.md` with a spawn prompt for each lead and its reports.
- **Node only, where it is cheap.** `scripts/agent-team/report.mjs` takes `team-status.sh`'s arguments and writes the same event without bash, `jq` or `curl`; `team-status.sh` hands over to it when `jq` is missing. `scripts/agent-team/sync.mjs` is `sync.sh` for machines without bash. [docs/windows.md](docs/windows.md) lists what runs on Node alone and what needs Git Bash or WSL.
- **`agent-team doctor`.** Checks the tools, that generated files and hooks are in sync, the roster and its hand-offs, and runs a hook event through the reporter into a scratch board. `--ping` posts a note to `TEAM_REPORT_URL`. Exits 1 on any failure.
- Tests: smoke scenarios (a new project reporting through its hooks, `team-status.sh` without `jq`, an agent-teams project passing `doctor` and `sync.mjs check`) and evals that every preset's roster, reporting lines, hand-offs and teammate exports hold together.
- Protocols: hooks are a safety net, not a substitute for the role's own start, wait and message reports.
- Generated scripts with a `#!` line are now executable.
- This repository runs its own team: `.agent-team/` (21 roles, with a `kit-core-dev` role of its own), generated `docs/team/` and `scripts/agent-team/`, and `sync.sh check` in CI. Nothing changes for other teams.
- The kit package no longer picks up generated scripts: `package.json` `files` lists `scripts/*.sh` instead of `scripts/`.
- CI checks the role library explicitly (`roster.mjs --check team/roles`), because `docs/team/roles` (this repository's own team) would otherwise be the default.
- Docs: the product plan for Agent Team Studio in `docs/product/` (PRD, architecture, deployment, delivery plan, how our own team builds it) and ADRs 0001 and 0002.
