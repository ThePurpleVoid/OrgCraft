# Changelog

## Unreleased

- **Studio: a send from a branch with an open change waits too** (L40b, CTO ruling). "Send them now" from any pushed, non-default branch stores a pending set bound to that commit instead of applying, with the PR number when `gh pr view` finds the branch's PR open (none, closed or unreadable: no number), so systems nobody has reviewed never widen a team's access; a detached HEAD waits too; only the default branch or a purely local branch sends directly. The ready line now says the report came from the team's own checks, which OrgCraft hasn't confirmed, with a tooltip (security review low). The send reads HEAD's sha once and the systems from that commit, so the two can't drift apart.
- **Studio: systems in PR mode wait, then the owner switches them on** (L40b web half). A publish that opens a change for approval sends its systems as a pending set bound to the commit (PUT `/v1/teams/{team}/systems` with `pending: { sha, pr }`, behind the `systems:<team>` step-up), and the result says they wait until the change is approved. GET `/v1/team/systems` shows the pending set (`ours` when it is what HEAD publishes, by content hash), what switching it on would change, and the code host's name. The start plan and the running header say the set is waiting; once the code host reports the change accepted, "Switch on now" applies it (POST `…/systems/pending/apply` with the sha and content hash shown) behind a fresh step-up whose dialog lists the changes. A set someone changed after it was shown is refused before any passkey. Chat shows "ready" and "dropped" (with the reason) as timeline lines.

- **Systems changes in PR mode wait for the merge** (L40b). `PUT /v1/teams/{team}/systems` takes `pending: { sha, pr? }` (with `expect`): the admin's step-up-confirmed set is stored bound to that commit and to the version it was confirmed against (migration 026, `team_systems_pending`, one per team). It becomes the team's systems only on a publish the server vouches for, and only if the base has not moved: a managed change the server accepts (its head or the commit main moved to), or `POST /v1/teams/{team}/systems/pending/apply { sha }`, an admin's "Switch on now" with a fresh `systems:<team>` step-up after the pull request merged. A report-token or posted `team.published` never switches anything on (any teammate can send one). The set is also bound to its content (`canonicalSystemsHash` from team-model): a CI publish (`report.mjs published` now sends `systemsHash`) whose hash matches marks it "merged, ready" (`pending.ready`, `by: ci`, and a `systems.pending.ready` event) for the admin to switch on, since a merge commit has another sha; the same pull request published with another hash drops it (`merged-different`); a publish with no hash is neither. Apply is allowed without the CI's mark (an admin with a step-up can set systems directly anyway) and the audit row records `ciReported`. Apply checks expiry and the base before the step-up is spent. The audit row names the commit, the confirming admin and who switched it on. A newer pending set replaces the older (never applied), a direct PUT drops it, `DELETE /v1/teams/{team}/systems/pending` drops it when the pull request closes, and it expires after 30 days (dropped at the next run start). Every drop is a `systems.pending.dropped` event (`sha`, `pr`, `reason`: withdrawn, expired, base-moved or merged-different); it and `systems.pending.ready` also show in `GET …/chat`. Apply takes an optional `contentHash` (the one shown) and answers 409 `pending-changed` if the set was re-confirmed with other content since. `GET …/systems` shows `pending`.

- **What a systems change widens: `systemsCapability(before, after)`** (L40, kit half; ADR 0013 rule 2). It takes two resources.json shapes, as GET and PUT `/v1/teams/{team}/systems` carry them, and lists what the change widens:
  - `system-added`: a new system, whether or not a seat is bound to it yet;
  - `binding-added`: a seat gets a system;
  - `binding-widened`: Read → Change → Act (read, write, deploy);
  - `resource-widened`: a system gains a secret, or its command, type or settings change. It is listed even when no seat is bound yet.

  Removing or narrowing lists nothing. `capabilityDiff` uses it for the systems part of a publish, so the Publish sheet and the PUT show the same items. `selfCapability` refuses a seat widening its own systems. **What existing teams see:** nothing on sync.

- **Sign-offs from the kit name the version they checked** (L23s, kit side; governance G1, for kit 0.23.0). `team-status.sh … signoff` takes `--version` (a full commit id or `HEAD`, which it resolves; a document's revision or draft with `--version-kind revision|draft`), `--result pass|fail` and `--unverified "…"` once per item not checked (`--unverified none` for an empty list; leaving it out means not stated). The report also carries `kit=<the kit's version>` from `.agent-team/kit.lock.json`, so the control plane knows the sender could name a version. A short commit id, an unknown kind or result, or more than 20 unverified items are refused with the reason before anything is sent. Sign-offs always go through the Node reporter, which checks them. **What existing teams see:** nothing on sync; old sign-off commands still report, and the control plane says what they leave out.

- **Control plane: sign-offs tied to a version, and the merge gate** (governance G1 and G2, L23 server half). `message.signoff` keeps `version`, `versionKind`, `unverified` and the runner's `checks` (only through a runner session; an `io` in them must be that session's own; a sign-off posted through the API loses them), and every message keeps `unverified`. When a pull request's head moves past a sign-off, the server emits the new `signoff.stale` once and wakes the role that signed. Approving a merge is refused (409, `type: signoffs`, with the list) until every sign-off on its pull request names the head, passed and says `Unverified: none`; the approval card lists the sign-offs with their versions and turns Approve off, with the reason, meanwhile, and refreshes as sign-offs arrive. Denying is never gated. The server stamps each sign-off's `origin`: `session` when a runner session sent it through the `signoff` tool, `reported` when it came through the API or a report token (whatever the sender wrote; the kit's own `source` label is untouched). Once a role has a session sign-off, the newest one is what counts, and a later reported one can only tighten it (a fail or unchecked items block; a reported pass never opens the merge). A role with no session sign-off is judged on its newest reported one, and the card labels it "reported, not run here". A reported sign-off is judged like any other: one with no version, no result or no Unverified line blocks, and from a kit before 0.23.0 (which can't name a version) the card says to upgrade the kit or sign off from a runner session. The card refreshes when a sign-off is reported too. A report's `signoff` row keeps `version`, `versionKind`, `result`, `unverified` (an empty list is kept: it means none) and `kit`. A sign-off that names a revision or a draft on a pull request is judged on its result and its Unverified line, not against the head. **What existing teams see:** on the hosted runner, a merge with an old, partial or unversioned sign-off on it now waits for a fresh one; a pull request with no sign-offs is unaffected; a kit team before 0.23.0 that reports sign-offs on a pull request the hosted runner merges sees them on the card, labelled, blocking until it upgrades or a runner session signs off.

- **Control plane: the budget day follows the team's time zone, a cap tree, spend leases and cost estimates** (L24s; vision G15.1 and G15.2; CTO review 2 R4 and R14; migration 019). `budgets.timeZone` (IANA, default UTC; changing it needs step-up) sets where the budget day starts and ends, 23 or 25 hours when the clocks change; today's spend, the 80% warning, the 100% pause, run day caps and meeting caps all use it, and `today` says `startedAt` and `resetsAt`. `GET /v1/teams/{team}/caps` (viewer) shows the cap tree: today's cap, each live run's and the meeting cap, with spent, held and left, and what happens at each step. A runner asks `spend.lease` before spending: it gets an amount from what is left, for five minutes, under a lock on the day, so two sessions can't both be given the last cent; usage counts against the lease, and a session that ends frees it. `GET /v1/teams/{team}/estimate?kind=meeting|trial|teammate` (viewer) says what one usually costs here (last 30 days), and whether it may not fit in what is left today; it warns, never blocks. - **Managed teams: change requests are accepted, closed and rolled back from the control plane** (no-repository start, step L9c; ADR 0012 and 0013, spec L9 sections 4.4 and 4.5). New routes: `GET /v1/teams/{team}/changes` and `/changes/{n}` (viewer), `POST …/changes/{n}/accept` (admin), `…/close` (editor) and `POST …/rollback` (admin). Accept runs the checks and the capability diff again at the change's head against the current `main`, then refuses, in order:
  - a stale base (409 `stale`, with `proposal.failed` head-moved);
  - red checks, or files that are not what sync writes (409 `checks`);
  - a change a teammate drafted that widens its own access or weakens a check (403 `self-widening`);
  - commands the team runs, from someone who is not an admin (403 `publish-code`);
  - a non-empty capability diff without a step-up scoped to this change (401, scope `accept-change:<team>_<number>`).

  Then `main` moves, fast-forward only. A pending audit row (the person's words and a hash of the diff) is written before main moves, then the outcome row, and `proposal.accepted` and `team.published` (id `published-<sha>`, via managed) are appended once. Rollback takes the old version's `.agent-team/`, syncs it with today's kit against `main` (so a version an older kit generated can still be rolled back to) and opens a change; rolling back to the current version is 409, so the access it puts back needs step-up again. `requireStepUp` takes an optional scope. **What existing teams see:** nothing; GitHub teams answer 409 on these routes.

  - `apps/server/managed-db.mjs` holds the Postgres refs and objects. The hosted Studio serves a team whose `backend` is `managed` without the GitHub App.
  - What the store holds clones with real `git`.

Three kinds are enforced now: `refund`, `pay.known` and `send.known`. `reply`, `merge` and `cost` come later. Every rule has a limit per calendar period in the team's time zone (a day from midnight, a week from Monday, a month from the 1st; `used.resetsAt` says when it resets) and lasts 1 to 90 days (30 by default). - **Control plane: the gateway paces calls and keeps every outward effect to one** (CTO review 2 R1a and R5, decision C1, local PR L20g; migration `024_gateway.sql`). Contracts additive. **What existing teams see:** nothing, until a runner calls the new ops; GitHub calls from the server may wait a moment under load.

## 0.9.2

### Security

- **DNS rebinding on the local dashboard and the Studio (severity 2). Every team should sync to 0.9.2.** A web page on a hostile domain whose DNS name resolves to 127.0.0.1 could call `scripts/agent-team/dashboard.mjs` or `agent-team studio` as if it were the same origin. It could read the board, post reports, and use the token these servers hold for a hosted board (`TEAM_READ_TOKEN`) or the control plane. Both servers now check the `Host` header on every request, static files included, before anything else runs:
  - Bound to a loopback address, they answer only `localhost`, `127.0.0.1` and `[::1]` (any port).
  - Bound to another address, they also answer that address. On `0.0.0.0` or `::` that means every address of the machine.
  - Each server also answers the names in its own allowlist, `DASHBOARD_ALLOWED_HOSTS` or `STUDIO_ALLOWED_HOSTS`.
  - Anything else gets 403. The Studio's Origin and JSON checks on POSTs stay as they were.
- **What existing teams see on sync:**
  - A new file, `scripts/agent-team/hosts.mjs`.
  - Threads on other machines that report to a dashboard started with `--host 0.0.0.0` keep working when they use its IP address. If they use a name (`TEAM_REPORT_URL=http://mac-mini.local:4747/...`, a VPN or tunnel name, a reverse proxy), set that name in `DASHBOARD_ALLOWED_HOSTS` on the dashboard machine; until then those reports get 403.
