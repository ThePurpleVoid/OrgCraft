# OrgCraft Studio: delivery plan

Owner: CTO. Status: draft 2, 2026-11-06 (online first, [ADR 0005](../adr/0005-online-first-built-to-last.md)). Each phase ends with a demo checkpoint against the [customer demo](prd.md#4-the-customer-demo-the-end-to-end-acceptance-test) and names the roles that carry it (see [how the team builds it](team.md)). Phases overlap where their owners differ.

| Phase | Outcome | Demo steps working | Gaps closed | Kit release |
| --- | --- | --- | --- | --- |
| 0 | Plan and our own team | none (this repository runs its own team) | none | none |
| 1 | Team model and lossless round trip | 7, 8 from the CLI | G1, G2 (with the kit thread) | 0.4 |
| 2 | Local editor, publish, live board, custom agents | 1 to 8, 13, 14 | G1 on the canvas | 0.4.x |
| 3 | Online foundation (control and data plane, Postgres, events, workflows, tenancy, OIDC), runner and chat, safe changes, meetings, email, mobile-ready API and mobile web control room | 1 to 12: **the full demo on an online deployment**, plus 15 to 17 | G2 run modes, G4 evals harness | 0.7 |

| 6 | Our hosted service, launched (owner's go on billing and terms) | the demo with no install | none | 1.0 |

## Phase 0: plan and our own team (this PR)

- The PRD, architecture, deployment and delivery plan in `docs/product/`, and ADRs 0001 and 0002.
- This repository runs its own team: `.agent-team/` (21 roles, pinned to kit v0.3.0), `docs/team/` and `scripts/agent-team/` generated by the kit's own `init` and `sync`, ownership for the kit and the Studio paths, CTO and CPO lane files, the kit gate in `config.sh`, and `sync.sh check` in CI.
- **Exit:** CI green including `sync.sh check`; the owner has the plan; the runtime decided (ADR 0002: our own runner on the Agent SDK).

## Phase 1: team model and round trip

Roles: kit core dev (lead), architect (schema review), test automation engineer (golden tests), release manager.

- `packages/team-model`: TeamSpec JSON Schema, `importLayer`, `validate`, `compile`, `build`. `bin/agent-team.mjs` uses it; behaviour unchanged.
- Optional new layer files: `ownership.json`, `gates.json`, `resources.json`, `studio.json`, each with sync support and docs.
- CLI: `agent-team import --json` (layer → TeamSpec) and `agent-team compile spec.json` (TeamSpec → layer). These help scripting, and give the Studio a CLI to test against.
- Golden round-trip tests: `examples/native-mobile`, this repository's `.agent-team/`, and every preset with and without subagents.
- Coordinated with the kit thread's 0.4 work: hook-based status (`report.mjs hook`, `source: "hook"`, `AGENT_TEAM_ROLE`) and the built-in agent teams export (`"agentTeams": true`) generated by sync, both in kit PR #10.
- Progress: kit 0.4.0 shipped the hooks, the agent teams export and Node-only reporting. The TeamSpec schema, `importLayer`/`compileLayer`/`resolveSpec`, the editing helpers, `agent-team import`/`compile` and the golden round-trip tests shipped in kit 0.5.0, with `ownership.json`, `gates.json`, `resources.json`, `studio.json` and `agent-team validate`. What is left of phase 1: CoachSpotter on 0.5 with a zero-diff sync.
- **Exit:** kit 0.4 tagged; zero-diff round trip on every golden layer; CoachSpotter upgrades to 0.4 with no change to its generated files except the new hook files.

## Phase 2: local editor, publish, live board

Roles: web dev (lead), design director and style threads (canvas visual language: 3 to 5 directions, the owner and the CTO pick), UX writer (copy table), design critic, backend dev (local server), QA web, code reviewer.

- `npx agent-team studio`: the local server (file access, WebSocket, `/api/report`) and the editor. Its code moves into the online Studio in phase 3.
- Canvas with Org and Flow views, palette, inspector, toggles, reporting lines by drag, live checks, undo/redo, auto-layout, templates from presets.
- Import any repository's `.agent-team/`; ownership table with suggestions from the repository tree; gates read from `config.sh` (read-only) and `gates.json` (editable).
- Publish: diff preview, local commit on a branch, PR through `gh`.
- Live board on the canvas from hook and role events (the kit dashboard's event model).
- **Custom agents** (PRD 6.6, A1 to A7; mockups 01 and 02): the New agent sheet (blank, copy a kit role, import a file), the guided editor with the live brief preview, path-conflict choices, "Your agents" in the library, role pack export and import, and the kit-upgrade shadowing check. Kit side: `## Sign-off evidence` and structured `## Wakes on` sections, `pack.json`.
- **Change safety, part 1** (PRD 6.9 X1, X5, X9; mockup 06): `diffTeams` and `impact` in `packages/team-model`; live status on canvas cards from board events; amber marks and the in-place explanation when a change touches a working role; the impact step in Publish in board-only form (warnings and the "data may be stale" note, choices recorded in the PR body).
- **Meeting definitions** (PRD 6.7 M8; mockup 03, editor half): the Meetings view edits `meetings.json`, with checks and the cost estimate. Running them is phase 3.
- Progress: kit 0.6.0 shipped `agent-team studio` with the library, the org canvas (drag to re-parent), the inspector, live checks, undo/redo and publish (diff preview, commit on a branch). It is plain ES modules with no build ([ADR 0003](../adr/0003-studio-local-mode-without-a-build.md)). Kit 0.7.0 added the Flow and Systems views (systems dragged onto roles with read, write or deploy), and the owned areas and checks editors with suggestions from the repository's folders and build files; the Studio's API is under `/v1/`. Still to do: custom agents, change safety part 1 with the live board on the canvas, meeting definitions, PR through `gh`, templates.
- **Exit:** demo steps 1 to 8, 13 and 14 on a sample repository, walked by QA web with screenshots; a usability test with 3 people that includes making one custom agent.

## Phase 3: online foundation, runner and chief-of-staff chat (the MVP)

Roles: architect (contracts), backend dev (control plane, lead for the foundation), AI engineer (runner, lead for runs), infra (images, Compose, one-click templates, staging), web dev (chat, approval cards, sign-in), security reviewer (tenancy, identity, approval policy, sandboxing), QA web, head of quality.

**Foundation, built in its final shape at small scale** ([ADR 0005](../adr/0005-online-first-built-to-last.md), architecture section 13):

- Contracts first, written and reviewed before code: the event envelope, the runner protocol, the connector capability manifest, the neutral work contract (`area`, `check`, `propose`, `accept`, `evidence`; ADR 0005 §8) with the repository connector as its first implementation, and `/v1/` of the public API (OpenAPI).
- Control plane (`apps/server`): Postgres with `tenant` on every row and row-level security; the event log as the system of record with projections; durable workflows (Postgres jobs and timers behind one interface); OIDC sign-in with GitHub; organisations, workspaces, members and roles.
- Data plane (`apps/runner`): runners connect outbound, authenticate, pull work and stream events; sandbox driver with process and container implementations.
- Connectors framework with one lifecycle and the vault; first connectors GitHub (App), email (provider API, SMTP fallback) and webhook.
- Shipping: signed `studio` and `runner` images, the Compose stack, a one-click template for one platform, `studio doctor`, a staging deployment in a real cloud account, and local mode as the same build with bundled Postgres. The phase 2 editor moves into the online Studio unchanged.

- Progress (2026-11-06): the owner started the MVP build, with an existing production kit team as the first real team on it. M1, the contracts, is in [docs/contracts/](../contracts/README.md), and `packages/events` maps the kit's reports to and from the event envelope exactly. M2, the control plane, is in [apps/server](../../apps/server/README.md): the event log on Postgres with row-level security per tenant, report intake that the kit's own `team-status.sh` uses unchanged, the board, the live stream, and sinks that keep a team's existing board fed.

**Runs, on top of the foundation:**

- `apps/runner` on the Claude Agent SDK: run modes subagents and Studio runner; the built-in agent teams export runnable from the Studio ("open in terminal").
- Team tool server (report, handoff, bug, signoff, blocked, ask_owner, request_approval, memory, open_issue, merge) with field checks.
- Message bus with wake-on-message; ownership-enforcing pre-tool hook; approval gates for the owner-steps-in list; budgets, caps, pause and stop; audit log.
- Chat: verbatim owner messages, decision and approval cards, daily digest, cost line.
- **Change safety, part 2** (PRD 6.9 X2 to X8, X10; architecture 12.4; mockups 07 and 08): sessions pinned to a team version; the live in-flight inventory; the impact step with per-item choices and recommendations; transition plans applied on merge; `checkpoint()`; temporary ownership rules; the invariants; the rollout view; impact cards for `.agent-team/` changes merged outside the Studio. Owned by the AI engineer (runner) and web dev (dialogs); security reviewer reviews the invariants.
- **Meetings** (PRD 6.7 M1 to M7, written round only; architecture 12.2; mockup 04): scheduler, recurring and ad hoc meetings (from the Meetings view and from the chat), busy-attendee handling, `meeting_reply` and `meeting_close`, minutes and action items in the chat, caps and skip-if-quiet.
- **Notifications** (PRD 6.8 O1 to O7 with email and webhook; architecture 12.3; mockup 05): the notifier, rules, quiet hours, delivery log, test sends, signed decision links. Slack waits for phase 4.
- **Try it on a task** for custom agents (PRD A8).
- **Ready for mobile** (PRD 6.10, architecture 14.2, [clients contract](../contracts/clients.md)): bearer tokens and PKCE public clients, the discovery document, `me/inbox` and `me/summary` projections with `asOf` and `ETag`, `events?after=`, structured cards with versions and `409` on stale answers, step-up on approvals, one deep-link URL per thing in every email, device registration and the `push` channel type in the notifier's model, idempotent writes. Owned by the architect (contract review) and backend dev; security reviewer reviews step-up and tokens.
- **Mobile web control room** (PRD MB11): home, inbox, board as a list, role page, chat, cards, minutes and run controls usable at 360 px; the editor read-only on small screens. Owned by web dev; QA web walks it on a real phone.
- Evals harness v1 on one sample repository: single agent vs subagents vs Studio runner, same model and budget.
- **Exit:** the full demo (steps 1 to 12) live on a fresh sample repository, with step 11's approval answered once from a phone browser, on a fresh online deployment in a cloud account (Compose or the one-click template) by someone who did not build it, following only the docs, three times in a row; the same build run locally; steps 15 to 17 walked once with no work lost (every stopped session's branch and memory checked); first evals report published in the repository, whatever it shows.

## Phase 4: systems and parallel roles

Roles: backend dev (connectors, vault), AI engineer (parallel sessions, worktrees), infra (Windows and macOS CI), kit core dev (Node scripts), security reviewer.

- Connectors: Supabase, Postgres, Vercel, generic MCP server, Slack (tools and notify); the Systems view with bindings.
- Terraform modules for AWS, GCP and Azure; the Helm chart; rolling upgrades that drain and checkpoint runners.
- Parallel role sessions with worktrees and hardware pools; concurrency cap.
- Kit 0.5: Node equivalents of `team-status`, `team-board`, `merge-gate`, `with-lock`, `janitor`; Windows CI.
- Discussion-format meetings and event-triggered meetings; Slack as a notification channel with buttons on decision cards; "freeze the team" (PRD X8).
- Evals on three sample repositories.
- **iPhone and Android apps v1** (PRD MB1 to MB10, MB12, MB13; [ADR 0006](../adr/0006-mobile-apps-native-per-platform.md)): the two repositories created, each with its own team lane, gates and release role; clients generated from the pinned `api-v1.yaml`; conformance fixtures in `docs/contracts/fixtures/` run by both; home, inbox, cards with biometric step-up, board list, role page, chat, meetings (read and speak by text), run controls, notification settings, deep links, the offline cache. `apps/push-relay` and push delivery in the notifier. Roles: iOS dev, Android dev, QA iOS, QA Android, design director (mobile screens from mockups 09 and 10), security reviewer (tokens, device keys, relay), release manager (store releases).
- **Exit:** demo steps 5 and 6 with real connectors; two builders working in parallel during step 10; the kit's tests green on Windows; demo step 18 on a real iPhone and a real Android phone against a self-hosted deployment, through the relay, with no team content in the push payloads (checked from the relay's logs).

## Phase 5: enterprise and scale

Roles: infra (lead), backend dev (identity, tenancy), AI engineer (runner protocol at scale), security reviewer, release manager, docs keeper.

- Private data plane: `agent-team runner join` for runners in a customer's VPC, outbound only; a laptop joining as a runner for its devices.
- SAML and other OIDC providers; per-tenant encryption keys; regions; tenant export and deletion; audit export.
- A second workflow engine adapter (Temporal-class) and a second model or agent runtime adapter, proving the interfaces hold.
- Microsoft Teams and Discord channels.
- Mobile, part 2: widgets and Live Activities (a running meeting, a rollout, today's cost), voice in meetings, App Intents and Android shortcuts ("what is my team doing?"), iPad layout tuned for the board, enterprise device management (managed configuration, require a managed device for approvals).
- The first business pack on the neutral core (from the kit's marketing, sales and support roles), with Drive and a CRM or helpdesk connector, and a Studio-managed team repository for customers who never use Git.
- First adapter for another coding agent (an `AGENTS.md`-style export of the briefs and protocols), with governance kept by CI and, where the agent supports it, the runner.
- **Exit:** the demo with the control plane in one account and runners in another (a stand-in customer VPC), with no source code or secret value crossing to the control plane, checked from the event log and network logs.

## Phase 6: our hosted service, launched (on the owner's go)

Roles: infra (lead), backend dev, security reviewer, general counsel and finance lead (opened from dormant if the owner wants a paid service).

- The same images, run by us: microVM sandboxes per run, managed Postgres with RLS, KMS, two regions, status page, on-call.
- Billing and terms if decided; SOC 2 when customers ask.
- **Exit:** the owner's decision. The architecture does not change for it; phases 3 to 5 already built every part in its final shape.

## How we keep the plan honest

- The chief of staff's daily digest reports by phase and by demo step.
- A phase is done only when its exit is walked and signed off with evidence, like any feature.
- Evals results go in the repository and the README, good or bad.
